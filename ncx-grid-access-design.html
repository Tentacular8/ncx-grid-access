The example network

Three grid sites, one data center, one corporate office. The addressing is deliberately awkward in the way real distribution fleets are awkward: every site is built from the same template, so every site uses the same three subnets. Sites are internally split into zones so that a compromised device at one cannot reach everything else in the cabinet.

Why the overlap does not matter

Secure Connect addresses things by name, not IP. SUB042-RTU and RCL118-RTU can both be 192.168.20.30 because nothing on the fabric ever refers to them by address. This is the single feature that saves you from renumbering hundreds of sites before you can build anything, and it is what lets every site run an identical three-zone template.

The zone template

192.168.10.0/24 is LAN-OT-APPS, for site servers, VMs and protocol gateways. 192.168.20.0/24 is LAN-OT-CTRL, for protection and control gear that nothing but a defined application should ever open a session to. 192.168.30.0/24 is LAN-AUX, for cameras, environmental sensors, contractor drops and anything nobody can positively identify. A site carries only the zones it needs. Every zone is a separate router LAN on its own physical port, so this works with unmanaged switches and does not depend on getting access to a managed switch. See Containment.

Containment, and what NCX does not do

The requirement behind this work is blast radius. If an endpoint at a site is compromised, it must not be able to reach the rest of that site, the other sites, or the corporate network. NCX answers three of those four. It does not answer the first one at all, and no amount of policy in NetCloud Manager will change that.

Four spread paths, and which mechanism stops each
Spread pathContained by NCXMechanismWhat it depends on
Site A device to Site B device Yes, by default Secure Connect denies site to site until a policy allows it Nothing. This is the shipped default and it is the strongest single thing NCX does for this requirement.
Site device into corporate or the data center Yes Deny-all access policy, resources are one directional grants Withdrawing the legacy corporate route. If the flat path survives, NCX is not in the way of it.
Corporate device into a site Yes Undefined gear is not addressable and does not resolve The same route withdrawal. See the cutover sheet.
Device to device inside one site No. Nothing. None. This traffic never leaves the site LAN and the gateway never sees it. Local segmentation. Router LAN zones, physical separation, or VLANs if you have the switch.

That last row is why sheet 3 is drawn in zones rather than as one flat LAN. Before zoning, a camera at 192.168.30.50 had an unfiltered layer 2 path to two protective relays. NCX made that camera dark to the outside world and did nothing whatsoever about the path to the relays.

Four tiers, ordered so the switch dependency comes last

Most of the containment value lands before anyone needs administrative access to a managed switch. That ordering matters when switch ownership sits with another team.

Containment tiers
TierWhatNeedsCloses
0 NCX deny-all between sites, plus withdraw the legacy corporate routes Nothing new Cross-site spread, site to corporate, corporate to site. Three of the four paths above.
1 OT and non-OT on separate router LANs and physical ports, zone firewall default deny between them Re-cabling and NCOS config. No switch administration. The corporate-or-contractor device at a site pivoting onto control gear. The most likely real version of the threat.
2 Hypervisor: separate port groups per zone, no bridged path between the OT virtual network and anything else You already own this VM to VM movement inside the virtualization host.
3 Per-function VLANs, port isolation for cameras and unidentified gear, ACLs between OT function groups Administrative access to the site switches Movement inside a single zone. The residue tiers 0 to 2 leave behind.
Why the router, not the switch, should be the boundary

Whatever device enforces the boundary becomes the thing an auditor asks about later, and it inherits the requirement load that comes with that role. If a managed switch enforces zone separation through VLANs, that switch is in scope. If the Cradlepoint is the single access point between zones and out to the fabric, the count stays at one box per site, on hardware already managed through NetCloud Manager. Tiers 0 to 2 above build that shape deliberately. Tier 3 then adds depth inside a zone without moving the boundary.

What zoning still does not fix

Devices sharing a zone reach each other at layer 2, and that traffic never reaches the router. Neither the zone firewall nor the Hybrid Mesh Firewall east-west inspection can see it, because inspection only applies to traffic that traverses the router. Contain by function group, then rely on host controls and physical access control inside a group until tier 3 is available. If a vendor presents east-west IDS or IPS as the answer to lateral movement inside a substation, that is the question to put to them.

System topology

Every site modem dials outbound to the Service Gateway. Nothing routes inbound, no site needs a static IP, and NetCloud Manager never carries user traffic. It only pushes configuration and policy.

Where the gateway lives

NetCloud Manager is always cloud. There is no on-premises NCM. The choice you actually make is where the Service Gateway runs, and it changes which features you get.

The conflict to resolve before you buy

The strongest OT argument for this product is isolated, agentless vendor access, and that is cloud-delivered only. The strongest argument for hosting it yourself is keeping the grid data plane and FIPS posture in your own building. Sheet 1 shows both at once, which is a real deployment shape but means two gateways and two licenses. Decide deliberately rather than discovering it in design review.

Under the modem

SUB-042 in detail, and the sheet that shows the limit of what NCX does. Two separate mechanisms are at work here. NCX decides who may reach this site at all, and each device behind the modem is either a defined resource or it is dark. The router zone firewall decides what may move between the zones once something is already inside the cabinet, and NCX has no view of that at all.

Practical notes on building this

Four things to get right. First, do not change a LAN IP after the router is onboarded as an NCX site, because it breaks the address bonding at the gateway. Pin the zone addressing before you onboard. Second, if a VM needs to initiate outbound, such as a historian pushing to the data center, that is a separate policy from anyone reaching in. Direction is not implied. Third, devices sharing one zone still reach each other at layer 2, and that traffic never touches the router, so neither the zone firewall nor the Hybrid Mesh Firewall east-west inspection will see it. Zoning contains movement between groups, not inside one. Fourth, confirm with the SE that onboarding a router as an NCX site does not constrain local multi-LAN and zone firewall configuration the way it already constrains tunnels, DNS and routing.

Site tags do the scaling work. SUB-042 carries substation, district-4, ncx-prod. RCL-118 carries recloser, district-4, ncx-prod. CREW-07 carries mobile, district-4, ncx-prod. A policy written against a tag covers every site that will ever carry it, including ones built next year.

Two traps in the tag model

First, ncx-prod has to be applied at onboarding, not later. Any site missing it is silently excluded from every machine-path policy, and the failure looks like a polling problem rather than a policy problem. RCL-118 exists in this example specifically to make that visible: it holds nothing but an RTU, so a missing tag takes the whole site off SCADA.

Second, the wildcard resource names below (*-HMI, *-RTU) carry the entire scaling story, and the published documentation only describes wildcards for FQDN destinations. If wildcards do not apply to named resources, every policy here has to enumerate sites and runs into the 20-entry ceiling almost immediately. Confirm this with the SE before designing around it.

Human paths (1, 2, 5)

Source is an identity claim from Entra ID or Okta, so MFA, conditional access, and the leaver process govern grid access for free. Move someone out of Relay-Techs and their access is gone at the next evaluation.

Machine paths (3, 4)

Source is one host address, destination is a named resource class on one port. Static, narrow, always on, and easy to defend in an audit. Do not attempt to put a user login in front of SCADA polling or historian collection.

Note the ceiling: 20 source entries and 20 destination entries per policy. Tags, not lists of site names, are how you stay under it.

Rule 5 does not work with the gateway on sheet 1

The clientless portal is available only in the cloud-delivered model. Sheet 1 draws a customer-hosted Service Gateway in your own data center, which cannot broker a clientless session. As drawn, this rule is aspirational. There are three honest ways to close the gap, and the evaluation covers the trade in Section 8: run the cloud-delivered model and give up the on-premises data plane and the FIPS option, run both models side by side and pay for both, or drop clientless and give vendors a jump host inside LAN-OT-APPS reached with the NetCloud Client. Pick one before this drawing goes to a vendor call.

Desk to substation HMI

An engineer sitting on the corporate LAN opens the HMI VM at SUB-042. This is the sequence that replaces "it just works because we're in the office."

  1. The client is already running

    On a managed laptop the NetCloud Client is always-on and starts with the machine. The engineer does not "connect to the VPN". There is no on/off ritual tied to being out of the office.

  2. Identity, not location, opens the door

    The client hands off to Entra ID. MFA and conditional access run exactly as they do for email. The returned assertion carries group = Grid-Engineering, which is the only thing policy 1 cares about.

  3. The token grants membership, not reachability

    NetCloud Manager issues a session token that lets the laptop join the Secure Connect network and shows it only the resources its groups allow. Joining the fabric still gets you nothing on its own.

  4. The name is the address

    The engineer opens sub042-hmi.grid.internal. That name only resolves inside the fabric, and it resolves to the right site even though RCL-118 and CREW-07 use the same 192.168.1.0/24 range.

  5. The gateway decides, every session

    Policy is evaluated top down at the Service Gateway. Policy 1 matches and the session is allowed and logged. Nothing about the laptop's IP address, subnet, or physical location entered the decision.

  6. Into the tunnel, out at the modem

    Traffic enters the GRE-over-IPsec tunnel to SUB-042, over whichever WAN is currently primary. The E3000 decapsulates and delivers to 192.168.10.21 in the LAN-OT-APPS zone, a VM on the host in the control cabinet, indistinguishable to the fabric from a physical PC.

  7. Everything else stays dark

    The same authenticated engineer cannot reach the camera, the spare address, or RELAY-A. The last one is blocked because relays belong to a different group. Not "blocked at a firewall": the names do not resolve and no route exists.

The point of the whole exercise

Steps 1 through 7 are identical from the office, from home, and from a truck. That is what collapses your two trust models into one. It is also the part your current architecture cannot reach without segmenting the corporate LAN itself.

The cutover that makes it real

Standing up the fabric changes nothing on its own. Until the old routed path is withdrawn, both doors are open and you have bought a second network rather than a private one.

Prove it one site at a time

Withdraw the legacy route for SUB-042 only and run a full monthly cycle, including a planned outage and at least one after-hours callout, before touching the second site. The test that matters is not "can the engineer get in"; it is "did anything quietly depend on the flat path that nobody documented."

When things break

The failure modes worth designing for before the pilot, not after.

Failure behavior
What failsWhat happensWhat you do about it
Primary WAN at SUB-042 DPD detects the dead peer; the tunnel tears down roughly 5 seconds after a failed check and traffic moves to the carrier B tunnel. Established TCP sessions drop and reconnect. Accept the reconnect for HMI work. Confirm the ADMS poll timers tolerate a 5 to 10 second gap.
Active Service Gateway The standby takes over, but it must sit in the same data center. There is no documented geo-redundant pair. The single largest design risk here. Price a second network for site redundancy and get the answer in writing.
Identity provider unreachable New authentications fail. Existing sessions continue until their token expires. Decide now what the storm-restoration break-glass path is, and test it while nothing is on fire.
Gateway hits its licensed ceiling At 10% over purchased throughput, excess traffic is not transmitted. This is traffic loss, not an overage invoice. Size for a restoration event when every site talks at once, not for an average Tuesday.
Someone edits the router directly NCX owns the tunnel, DNS, and routing config on an onboarded site. Local IPsec/GRE edits, Umbrella, or a LAN IP change break the site. Lock local config change control the day you onboard. This is a process fix, not a product setting.
A device is added at a site Nothing reaches it. Not a fault. It is the default. Add "define the resource in NCM" to the commissioning checklist, or field crews will report the fabric as broken.

Where NERC CIP touches this

Every site in this example is a low impact BES Cyber System. That single fact decides which standard applies, and it is the reason this section is short. Low impact sites do not require an Electronic Security Perimeter. Medium impact sites do, and the fleet plan for medium sites is not settled, so this section states what is true now and marks the rest as open.

What applies at each impact level
 Low impact, the fleet todayMedium impact, planned but not scoped
Governing standard CIP-003 R2 Attachment 1 CIP-005, plus the rest of the medium impact set
ESP required No Yes, for every applicable Cyber Asset connected by a routable protocol
Electronic access controls Attachment 1 Section 3. At assets with external routable connectivity, permit only necessary inbound and outbound access, authenticate remote users, protect authentication in transit. ESP with identified Electronic Access Points, inbound and outbound permissions documented by reason, everything else denied.
Remote access for people Covered by Section 3. No Intermediate System requirement. Interactive Remote Access must terminate at an Intermediate System, be encrypted, and use multi-factor. Applies where the site has external routable connectivity.
Vendor remote access Attachment 1 Section 6. Determine active vendor remote access, be able to disable it, detect malicious inbound and outbound communication tied to it. Enforceable since 1 April 2026. CIP-005 R3, the same two capabilities, determine and disable.
Log retention Not specified at this level CIP-007 R4.3, 90 days of retained logs

What NCX gives you, and what you still owe

Low impact obligations mapped to this design
ObligationWhat this design providesEvidence you still have to produce
Attachment 1 Section 3, necessary inbound and outbound only Deny-all by default with an ordered, first-match policy. Undefined gear is not addressable and does not resolve. An exported policy set showing the reason for each rule, and evidence that the legacy corporate route is actually gone. Until it is withdrawn, the flat path is the real access control and the policy set is decoration.
Section 3, authenticate remote users SAML to Entra ID or Okta. MFA, conditional access and the leaver process are inherited from the IdP rather than reimplemented. The IdP configuration, the group-to-policy mapping, and evidence that removal from a group actually removes access.
Section 6, determine active vendor remote access Vendor sessions are brokered and per-session, so they are enumerable rather than inferred from firewall logs. A named report or console view, and a named person who checks it. Note that the clientless portal is cloud-delivered only, so if the design settles on customer-hosted, this obligation needs a different answer.
Section 6, disable vendor remote access Per-session evaluation with instant revocation, and group removal at the IdP as the second lever. A written procedure with an owner and a target time, and one tested revocation per year. Model the 90-day ZTNA licence reservation against contractor churn while you are at it.
Section 6, detect malicious vendor communication Not provided by default. Hybrid Mesh Firewall adds IDS and IPS, at extra licence cost, and only for traffic that crosses the router. The detection method, and the export path to a SIEM. ZTNA logs have no built-in long-term retention, so the export is part of the build, not a later improvement.
Open, and worth settling before the medium sites arrive

Whether the plan is to reclassify these sites or to take on net new ones changes the answer, because reclassification means retrofitting an ESP into sites already built. Design the boundary at the router now, in the shape on sheet 3, and the ESP is mostly already there when it is needed.

The cloud-delivered model becomes hard to defend at medium impact. The Service Gateway performs electronic access control, and at medium impact the ZTNA broker also sits in the Interactive Remote Access path. Placing that function in a vendor cloud is the open question NERC has not resolved, and it is being actively drafted rather than settled. Customer-hosted avoids it and cannot do clientless vendor access. That trade is Section 4, and the medium plan decides it.

Distribution is not automatically out of scope. A Distribution Provider is in scope for specific systems: UFLS and UVLS programs meeting the criteria, each RAS subject to a standard, Protection Systems applying to Transmission, and blackstart Cranking Path elements. The site inventory needs an impact classification column supplied by compliance, not an assumption supplied by network engineering.

None of the containment work in Section 2 waits on any of this. Segmentation for blast radius is a security control you own outright, and building it at the router now is also the cheapest path to an ESP later.
